# 小游戏美术协作、阶段品质与轻量资源

本文件补充 [WORKFLOW.md](WORKFLOW.md)，适用于已有原型后的美术、UI、动效与特效工作。方法依据为 `E:/Code/LittleGameDoc/Doc/GAME_DESIGN_CHARTER.md`（已完整阅读第 0—7 节）。具体游戏仍以自己的 AGENTS、产品入口、STATE、当前路线和用户最新指示为准，不重写已确认玩法，不凭“已有模型”猜测前置门已通过。

## 分工与平权

| 角色 | 领域责任 | 按需技能 |
| --- | --- | --- |
| game-producer | 玩法、数值、版本范围、节奏与整体体验评估；记录 STATE | game-design |
| game-art-lead | 美术方向、统一样板、资产规范与美术质量；协调专业分工 | game-art、create-game-assets |
| game-asset-artist | 原画、角色、物件、场景、图标与可导入资产 | game-art、create-game-assets、内置 imagegen |
| game-ui-artist | HUD、菜单、界面美术、布局和完整交互状态 | game-ui-ux；需要图像时 create-game-assets/imagegen |
| game-vfx-artist | UI 动效、命中/获取/结算反馈、粒子及必要材质 | game-feel；确需材质时 shader-programming |
| game-tech-lead | 唯一技术集成负责人，资源预算、接口、worktree、PR 审查与合入 | 按当前接入需要 |
| game-developer | 认领的运行逻辑、资源接入、平台适配及修复 | 按当前实现需要 |
| game-verifier | 独立评审或验收，检查明确版本及游戏内效果 | game-design；按风险读取美术技能 |

- 制作人与美术领域平权。美术 lead 是领域协调者，各美术专家对专业判断有直接质疑权；制作人继续评价美术是否支持玩法与整体体验，但不能仅凭个人审美推翻已确定的样板。美术方也不能擅自改变核心机制或扩大版本范围。
- 技术 lead 对集成、引用和性能负责；性能疑虑用实际基线、最小样件和降级方案讨论，不能把“感觉太重”当实测。单写入 STATE 是记录职责，parent_run 是任务关联，均不代表专业领域的上下级。
- 分歧先对照目标与已有约束，再用实际手机尺寸截图、可操作样件、前后对比及性能/成本证据解决。普通风格、配色与可逆参数已授权团队自主选择并记录；只有无法兼容且涉及核心卖点、版本范围、平台或新增预算的改变才交用户裁定。
- 并发按实际额度分批：通常先 producer 与 art-lead 对齐一个短切片，再并行 1—2 个互不冲突的专业任务；结束后释放实例，再启动独立验收。不要为凑齐岗位同时占满实例；无需常驻全部八种角色。

## 工作顺序与产物

1. 检查当前可运行版本、截图、已有资源、玩法与路线；确认本次要解决的视觉/理解/反馈问题，沿用一致的既有风格。尚无风格时给 2—3 个小方向并由 art-lead 与制作人选一个，不要求用户逐张审批。
2. 切片优先覆盖一个典型可玩场景、主要 HUD、一个代表性角色/物件及一次核心反馈，具体数量随游戏类型裁剪。先补影响该切片的前置缺口，不自动重做全部原型或跳到后续里程碑。
3. 在原有设计文档中记录简短视觉规范：视角、形状、色彩职责、轮廓/细节、光向、比例、参考显示尺寸与动效节奏。没有合适记录位置时仅新增 `docs/art/ART_DIRECTION.md` 与 `ASSET_MANIFEST.json`，不新增进度账本。
4. 制作真实样件并放入游戏检验；选定样件后以它为参考继续制作第二个同类样件，核对风格、导出/接入成本是否可重复，再按清单小批量扩充。同一切片已有有效复现证据时各岗位共同复用，不机械要求每个岗位额外制作第二套。只产出提示词或静态大图不能报已完成游戏美术。
5. 每项资产记录 ID、用途、源文件/导出文件、像素尺寸、原生显示尺寸、alpha、锚点/基线、帧数/时长、图集/加载组、压缩体积、纹理内存估算、来源/授权或生成记录及验收状态。先用技能模板，删去当前无用字段；估算与实测分开。
6. 游戏内查看原生尺寸、动态重叠、UI 全状态、连点与中断，再作必要的一轮修正及独立验收。交付运行入口、版本、前后效果、资源增量、检查与未测范围。

## 制作人的质量标准：严格到当前承诺

| 阶段 | 必须守住 | 可留后续 |
| --- | --- | --- |
| 玩法原型 | 开始—行动—反馈—推进—结果/回访闭环；目标与操作可理解；关键状态正确 | 全量成品美术、皮肤库、非必要系统 |
| 美术代表切片 | 游戏内风格统一、原生尺寸清晰、交互状态完整、关键反馈成立，性能/加载未出现不可接受退步 | 全关卡替换、所有次要动画与装饰 |
| 批量生产 | 第二样件能复现质量；导出、引用、授权与预算可控；每项内容有用途 | 凑数量、低价值变体与未激活内容 |
| 抖音交付 | 对应平台构建、开发者工具及目标真机证据；触控、安全区、恢复、加载失败处理符合约定 | 未承诺设备、后续平台及无证据的品质口号 |

- 分开评估程序正确、玩家可理解、目标体验是否得到支持。功能数、图片数、漂亮概念图和类型检查都不能替代这三种证据。
- 每轮只突出最影响当前成果的 1—3 个问题，标明复现、影响和最小改法；结论用“通过 / 带明确遗留通过 / 阻断当前切片”。阻断要对应当前承诺；主观偏好、轻微装饰瑕疵和后续内容列遗留。
- 普通打磨以 1—2 轮收敛为目标；崩溃、数据破坏、无法推进、严重信息误导与明显性能退步仍须解决，不能为赶轮数放行。持续不成立时缩小切片或做最小实验，不无限精修。
- 缺真机/真人证据可交付已验证的局部成果，未测范围保留待验；不能声称“已上抖音”“真人觉得好玩”或整阶段通过。正式 verification 仍由独立 verifier 对明确合入 SHA 执行。

## 资产、UI 与特效约束

- 实际生图/改图读取当前环境的 imagegen 技能并用内置工具；透明素材启用工具原生透明选项，检查 alpha 与实际尺寸。工具不可用先完成规范和清单，说明缺口；不假装已出图，不自动购买服务或转 API。
- 简单几何与引擎 UI 用可编辑的原生控件/代码；文字、数字和动态状态不烘焙进生成图片。复杂原画用位图；概念图只作参考，不能当可点击的整屏 UI。
- UI 覆盖普通、按下、选中、禁用及当前流程需要的空态/加载/失败态；检查长文本、大数字、窄屏/长屏、安全区、手指遮挡与误触。重要信息至少有颜色之外的形状/文字等线索；不为抖音触控首发强加手柄/TV 兼容。
- 动效先定义触发事件、时长、强度、取消与复位，再选 Tween、少量池化粒子或小贴图；有明确收益才写 Shader。高频反馈克制，不默认每次点击震屏/停顿；关键数值、目标与操作不能被遮挡。
- 表现与结算分离；动画取消、重试、节点回收、切后台后不遗留效果，不重复扣费/发奖，不锁输入。提供低配/减少闪烁与震动的简单降级方案。
- 技能示例主要来自 Unity/Godot；当前项目为 Cocos Creator 3.8.8 / TypeScript，版本核对项目 package.json。具体控件、图集、Tween、材质语法与构建方式查对应版本官方文档，不能直接粘贴异引擎代码或引入它们的依赖。

## 抖音轻量资源原则

- Agent TOML、skills、参考图、PSD 和生成工具是开发期内容，不复制到游戏 `assets` 或发布包。运行时仅加载实际需要的导出资源，不因使用 AI 制作就引入运行时 AI 服务。
- 先量出引擎/现有逻辑基线，由 tech-lead 与美术方设本切片预算并留余量；不能把平台上限当目标。分别记录代码主包、首局前实际下载字节、后续资源、解码后纹理内存、帧时/draw calls 和冷启动到可交互时间。
- 2026-10-22 核验的普通 JS/Cocos 小游戏规则：不分包总包上限 20 MB；分包主包不超过 4 MB、整体包默认不超过 20 MB，虚拟支付场景有 30 MB 规则。见[官方代码包说明](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/framework/subpackages)。发布时复核当前规则与实际账号，不混用 Unity 专用 100 MB 首包说明。
- 首屏/首局只载必要资源；后续页面/关卡按流程延后或分包加载，注意共享资源重复打包、预载时机、引用释放、缓存版本和下载失败回退。需要远程 CDN 时先核对现有平台方案及域名配置，不擅自新增服务。
- 优先合适尺寸、九宫格、图集与复用；图集也会形成加载整体，不能为减少 draw call 把全游戏塞成一个巨图。避免超大背景、长序列帧、全屏多层透明混合和无界粒子。
- 压缩 PNG 文件只减少下载字节，不自动减少解码内存；RGBA8 的基础估算为宽×高×4 字节，mipmap/多副本另算，适用的 GPU 压缩纹理按设备支持验证。用实际导出包和目标设备检查，不承诺“小游戏一定很轻”。参考[官方性能优化](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/optimization)。

## 文件交付与八岗位上报

- 候选方案先放本机暂存或已有设计位置。进入正式 Git 资源目录的美术修改也由唯一 tech-lead 分配独立 worktree/分支和文件归属，以 PR 交付、审查检查后合入；不在他人主工作区直接覆盖。场景、Prefab、.meta 同时只能有一个写入者；保留 UUID，生成导入元数据后检查引用。
- 美术 lead 协调美术工作，tech-lead 仍是唯一代码集成负责人；原画/UI/VFX 可以并行生产互不冲突的资产，运行脚本接入由技术线安排。没有实际实现工作时不为评审额外启动开发。
- 八岗位使用各自真实 `role` 沿用 v1 事件字段。四个美术岗位分别使用 `--role game-art-lead`、`game-asset-artist`、`game-ui-artist`、`game-vfx-artist`，不借用 `game-developer`；`instance` 标识具体执行实例，摘要描述实际任务，不承担补造岗位身份的职责。历史记录保留原角色，不按摘要推断改写。
- art-lead 的 parent 可为本切片制作人或 tech-lead run；资产/UI/VFX 的 parent 可为制作人、tech-lead 或 art-lead run。parent 表示任务来源并继承项目与两级阶段，不表示领域上下级；不能借用其他项目/阶段的 run。无合适 parent 时按原 begin 支持提供完整项目/阶段。正式验收仅挂制作人，不能挂实现者或美术 lead。
- `lead` 字段只表示技术负责人：新执行仅 `role == game-tech-lead` 为 true，art-lead 为 false；旧 developer+lead=true 仍按历史事实兼容。美术协调职责由真实 role 表达，不借此绕过唯一技术集成负责人。
- 美术方案/方向评审为 begin → checkpoint → stopped；四个美术岗位的正式资产或样件包均可用 submitted 交付给技术线，仍非验收通过。仅独立 game-verifier 在 acceptance 中使用 verification/verdict。离线有界排队，不阻断工作、不伪称 sent；维护角色或看板不自动创建游戏上报或改变游戏 STATE。

技能来源、安装路径及角色映射见 [SKILLS.md](SKILLS.md)；可直接使用的后续提示词见 [START_ART.md](START_ART.md)。
